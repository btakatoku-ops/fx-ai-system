# 構成

## 何をするものか

相場を分析して **BUY / SELL / WAIT / NO_TRADE** のいずれかを返す。
発注はしない。Phase 1 の範囲に自動売買もブローカー接続も含まない。

判断の優先順位は最初に決めてあり、実装もその順に並べてある。

1. 資金を守ること
2. 市場データが正しいこと
3. 「取引しない」を検出できること
4. リスク管理
5. シグナルの質
6. 期待値が正であること
7. 勝率
8. 見た目

上ほど強い。**7 の勝率のために 3 を緩めることはしない。**

## 層

```
config/*.json          売買ロジックの値（版管理する）
        │
backend/app/config.py  唯一の読み込み口
        │
        ├── market_data.py      供給元の抽象。mock / csv / 未実装の3種
        ├── indicator_engine.py 指標の計算（純関数）
        ├── market_structure.py HH/HL/LH/LL と BOS/CHOCH
        ├── regime_engine.py    相場つきの判定
        ├── filters.py          強制の見送り条件 ★ 点数とは別系統
        ├── signal_engine.py    向きの判定・100点の配点・最終シグナル
        ├── analysis.py         1銘柄ぶんの組み立て
        ├── pair_ranker.py      26銘柄の並べ替え
        ├── backtester.py       過去の足での検証 ★ 未来を見せない供給元を挟む
        ├── performance.py      成績の集計と比較
        └── main.py             FastAPI の口
        │
frontend/              Next.js。読み取り専用の表示
```

### 依存の向き

下から上へは呼ばない。`indicator_engine.py` は設定も供給元も知らず、
数列を受けて数列を返すだけにしてある。試験でこの層だけ切り離して
確かめられるようにするため。

## 強制条件と点数を分けてある理由

`filters.py` と `signal_engine.py` は別ファイルで、合流するのは
`decide_signal()` の1か所だけ。そこでの順序はこうなっている。

```
強制の見送り → 点数の区分 → 向き
```

**点数がいくら高くても強制の見送りを上書きできない。** 95点でも、
スプレッドが上限を超えていれば NO_TRADE になる。1つの関数に混ぜると、
重み付けの調整で強制条件を薄めてしまえる。分けてあるのはそれを
構造的に不可能にするため。

## 失敗したときの既定値

`analyze_pair()` は全体を try で囲み、何が起きても `NO_TRADE` を返す。
例外を握りつぶすのではなく、記録したうえで「取引しない」に倒す。

- 供給元が落ちている → NO_TRADE
- 足が足りない → NO_TRADE
- 指標が計算できない → NO_TRADE
- 想定外の例外 → NO_TRADE（`warnings` に内容を載せる）

**分からないときは動かない**、が既定の挙動になる。

## 安全境界（Phase 1 の要）

**危ない状態を「気をつけて避ける」のではなく、通らないようにする。**

### 1. 供給元の境界で止める

外から入ってきた値は、`Candle` / `Quote` を作る時点で確かめる。

- 有限であること（**`inf` は `v > 0` を通ってしまう**。通せば ATR も EMA も
  `inf` になり、以降の比較がすべて無意味なまま計算が続く）
- 価格が正、`high >= max(open, close)`、`low <= min(open, close)`
- 時刻が時刻帯つき、昇順、重複なし
- `ask >= bid`

壊れた足は上の層へ渡さない。**捨てて記録する。埋めない。**

### 2. 足の素性を確かめる（`freshness.py`）

**本数が揃っていることと、正しい足であることは別。**
H1 を頼んで2時間間隔の足が240本返ってきても、本数だけ数えれば「揃っている」
になる。指標は1時間足のつもりで計算され、画面には何事もなく点数が出る。

- 足の間隔が、その時間足として正しいか
- 抜けている区間が、**週末の閉場**で説明が付くか（付くなら欠落と数えない。
  数えれば月曜の朝は必ず「壊れている」と言い出す）
- 未来の足が混ざっていないか
- 最後の足が**確定しているか**（時刻 T の足が確定するのは T + 期間）

### 3. 鮮度は「取引時間」で測る

**壁時計で測ると、毎週月曜の朝に必ず壊れる。**

日曜22:00の再開直後、直前の H4 足は52時間前になる。許容が「3本ぶん＝
12時間」なら、正常な足が「古すぎ」で弾かれ、**全銘柄が止まる**。
市場が閉まっていた時間は、データが古くなった時間ではない。

`market_minutes_between()` が閉場帯を除いて経過を数える。週末をまたいだ
52時間は取引時間では4時間になり、許容に収まる。一方、平日18時間の空白は
そのまま18時間として検出される（**本当の欠落は見逃さない**）。

休場日は `config/market_calendar.json` に持つ。**入れてよいのは為替市場
そのものが実質閉まる日だけ**（元日・クリスマス）。各国の銀行休業日
（Thanksgiving、Bank Holiday、日本の祝日）は流動性が薄くなるだけで市場は
開いているので入れない。閉場として扱うと、**その日の本当のデータ欠落を
見逃す**。

### 4. 有効期限（`valid_until`）

**依存しているものの中でいちばん早く切れるものに合わせる。**

```
valid_until = min(いま + 分析TTL, 気配値の時刻 + 気配値の上限, 次の足)
```

分析の寿命が60秒でも、使った気配値があと10秒で古すぎになるなら、
この判断も10秒で終わり。長いほうに合わせると、**すでに根拠が失われた BUY を
画面に出し続ける**ことになる。

期限は**作った時点・APIが返す時点・画面に出す瞬間**の3か所で確かめる。
切れていれば BUY/SELL を残さず NO_TRADE に落とす。

### 5. 失敗の隔離

| どこで | どうなるか |
|---|---|
| 供給元が落ちている | その銘柄が NO_TRADE |
| 足が不正・不足・古い | その銘柄が NO_TRADE |
| 指標の計算が失敗 | その銘柄が NO_TRADE |
| 想定外の例外 | その銘柄が NO_TRADE（他の25銘柄は返す） |
| CSV 取り込みの不正入力 | HTTP 422 |

`pair_ranker` はペアごとに例外を囲む。1件壊れても **26件返す**。
壊れたペアも消さず、理由付きで下位に残す。

### 6. 記録

`reason_code`（`HARD_FILTER` / `STALE_DATA` / `NATIVE_TIMEFRAME_MISMATCH` …）を
pair・時刻とともに JSON 1行で残す。**文言だけだと、表現を変えたとたんに
集計が壊れる。** 秘密は書き出す前に伏せる。

## 同じ計算を繰り返さない

26銘柄の一覧を開いている最中に詳細を開くと、**同じ分析が何本も並走して
全部が遅くなる**。実測で、1件 0.54秒の詳細が同時要求下で 4.0秒になった。
要求が積み重なれば60秒に届く。

### 直したこと

| 内容 | 効果 |
|---|---|
| `_enrich` の転換点の二重計算を除いた | 1分析で9回→5回 |
| ボリンジャーを移動和にした（O(本数×期間)→O(本数)） | 4.3倍速く、値は同一 |
| `analysis_service` を1つの入口にし、短い寿命で使い回す | 一覧と詳細が計算を共有 |
| 銘柄ごとの錠で同時要求を1本にまとめる | 並走をやめる |
| 画面の2要求を直列から並列に | 待ち時間が半分 |

### 安全の条件は緩めていない

| 守ること | どうしているか |
|---|---|
| 期限切れを返さない | TTL 内でも `valid_until` を過ぎていれば捨てる |
| 時計の巻き戻しを許さない | `0 <= 経過 < TTL`。負なら捨てる |
| 強制条件はそのまま | 結果を書き換えない。使い回すだけ |
| 明示の時刻では使い回さない | 検証で過去の時刻を渡した結果を「いま」に混ぜない |
| 供給元が違えば分ける | 鍵に供給元の実体を含める（名前だけだと、壊れた供給元が正常な結果を受け取る） |

使い回しの寿命（`cache_ttl_seconds`）は判断そのものの寿命
（`analysis_ttl_seconds`）以下にする。試験で固定してある。

## 検証だけは判断の外から挟む

`backtester.py` は `analyze_pair()` を**一切変えずに**過去を再生する。
`HistoryProvider` が供給元を包み、指定時刻より後ろの足を返さない。

```
backtester → HistoryProvider(cutoff=T) → analyze_pair（そのまま）
```

判断側に「検証中かどうか」を持ち込まない。持ち込むと、検証のときだけ
通る道ができて、本番と違う挙動になる。**未来を見ないことは、判断側の
心がけではなく、渡すデータの形で保証する。**

## 設定の置き場

売買ロジックの値は `config/*.json` に置き、**版管理する**。
しきい値をコードに散らすと、いつ何を変えたか追えなくなる。

環境ごとに変わる値（接続先・ログ水準・供給元の選択）だけを環境変数にする。
秘密はコードに書かない。`.env.example` は雛形で、`.env` は版管理しない。

`_` で始まる鍵は読み込み時に落とす。設定に注記を書けるようにしてあるが、
それをデータとして読むと壊れる。実際 `min_candles` の `_comment` を
時間足として扱い、**全26銘柄が見送りになる**不具合を出した。

相対パスは起動位置ではなく **プロジェクト基点** に付ける。
`backend/` から uvicorn を起動したときに `backend/database/` が別にでき、
同じ設定なのに中身が違う状態を作ってしまったため。
